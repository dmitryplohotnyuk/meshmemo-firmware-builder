# Анализ flash-копии и план обновления

`inspect-flash` и `plan-update` работают с локальными файлами. Python 3.11+
достаточно: PlatformIO, esptool, Git и подключённая плата для этих команд не нужны.
Команды не открывают serial port, не обращаются к серверу и не записывают flash.

`plan-update` принимает образы профиля `meshmemo` со встроенным build ID.
Профиль `patches-only` намеренно не добавляет этот идентификатор и USB-протокол;
его manifest отклоняется с отдельным пояснением. Проверка backup через
`inspect-flash` и операции восстановления от профиля сборки не зависят.

Те же действия доступны пошагово в `meshmemo-builder wizard`: «Проверить
обновление по flash-копии», «Создать пакет восстановления» и «Проверить пакет
восстановления». Мастер показывает краткий результат; для плана обновления можно
сохранить полный JSON-отчёт, в том числе с причинами блокировки. Плата выбирается
явно, опции готового образа берутся из manifest. Для скриптов используйте обычные
команды ниже. Отмена через `q`, EOF или Ctrl+C возвращает код `130`.

## Просмотр резервной копии

Нужен полный сырой дамп flash, считанный с адреса ноль. Экспорт настроек,
application-only `.bin` и factory image не являются такой копией.

```sh
meshmemo-builder inspect-flash --backup backups/flash-before.bin
meshmemo-builder inspect-flash --backup backups/flash-before.bin --output inspection.json
```

JSON содержит размер и SHA-256 копии, таблицу разделов, результат проверки её
MD5, выбранный по OTA-метаданным раздел, размер и хеш установленного приложения.
Содержимое NVS, файловых систем и каналов в отчёт не включается. Сама flash-копия
может содержать ключи и личные данные: храните её вне Git, например в `backups/`.

Поддержан формат ESP32-S3: дампы размером 1–32 МиБ, степень двойки, таблица по
`0x8000` с MD5. Проверяются границы, выравнивание, перекрытия, дубли разделов;
у приложения — заголовок, сегменты, app descriptor, XOR checksum и SHA-256.
Изменённый формат, отсутствие MD5 или неверный размер файла дают ошибку.

OTA-выбор учитывает две записи с CRC и последовательностями, factory-раздел
и последовательные OTA-слоты. Неоднозначные/повреждённые метаданные, незавершённая
валидация, rollback-состояния и неподдержанные flags блокируют план. Это
консервативная проверка: автоматический fallback загрузчика не моделируется.
Выбор по копии **не доказывает**, какое приложение сейчас запущено на устройстве.

## Сопоставление с новой сборкой

```sh
meshmemo-builder plan-update --board tbeam-s3-core --backup backups/flash-before.bin --manifest dist/custom/manifest.json --output update-plan.json
```

Для Heltec укажите `--board heltec-v3` и manifest соответствующей сборки.
Плата задаётся явно: ESP32-S3 chip ID не различает зарегистрированные модели.
Новые профили `heltec-wsl-v3`, `heltec-wireless-tracker` и `tlora-t3s3-v1`
используют ту же проверку образа, но собственные model/build ID и manifest.
Имя платы, upstream, профиль, опции и build ID сверяются с реестром сборщика.
Сам `.bin` должен лежать рядом с manifest; проверяются его размер, SHA-256,
формат application-only и наличие ожидаемого build ID. Factory-файлы, подписи
после образа и планы от несовместимого реестра отклоняются. Хеши подтверждают
согласованность файлов, но не удостоверяют автора сборки.

Опции UA22, кириллицы и таймера дисплея берутся из manifest. Команда их не меняет
и не предполагает, что они включены на старой прошивке.

Если проверки проходят, `status=offline-compatible`. В `proposed_write` записаны
адрес выбранного раздела, размер образа, округлённый до сектора диапазон стирания
и запас места. Используется **разметка копии**, даже если раздел новой сборки
больше. `rollback` связывает план с исходной копией и проверенным приложением.
Команда не извлекает и не создаёт образ для отката.

Если разметка/OTA или размер не подходят, `status=blocked`, причины находятся в
`blockers`, а `proposed_write=null`. Смена разделов или стирание всей flash
автоматически не предлагаются.

Оба результата содержат `device_accessed=false`; план всегда содержит
`flash_authorized=false`. Перед реальной записью нужны актуальная идентичность
платы, свежая копия, текущие разделы/OTA, параметры чипа и eFuse, состояние secure
boot/encryption/anti-rollback, отдельная копия настроек и свободный serial port.
После записи нужны проверка хеша, загрузки, настроек и MeshMemo capabilities.
Сохранение data-разделов при записи не исключает миграцию настроек новой прошивкой.

## Пакет восстановления

Подготовка и проверка также работают offline:

```sh
meshmemo-builder prepare-recovery --backup backups/flash-before.bin --destination backups/tbeam-recovery
meshmemo-builder verify-recovery --package backups/tbeam-recovery
```

Родительский каталог назначения должен существовать, сам каталог пакета — нет.
Существующая папка, даже пустая, не используется повторно. Исходная копия
читается один раз: проверка, извлечение и копирование используют одни и те же
байты. При блокирующих условиях из `inspect-flash` пакет не создаётся.

| Файл | Назначение |
| --- | --- |
| `flash-backup.bin` | Полная исходная flash-копия, побайтно без изменений |
| `rollback-app.bin` | Приложение из выбранного factory/OTA-раздела, включая checksum и SHA-256 |
| `recovery.json` | Адрес, размер, диапазон стирания, разметка и контрольные суммы |
| `README.md` | Инструкция проверки и условия отдельного ручного восстановления |
| `SHA256SUMS` | SHA-256 четырёх остальных файлов |

Пакет самодостаточен: после переноса в другую папку исходный файл для проверки
не требуется. `verify-recovery` повторно разбирает полную копию, проверяет
приложение и сопоставляет его побайтно с исходным диапазоном. Адрес и хеши
вычисляются заново, а не принимаются из manifest. Для схемы 1 metadata,
инструкция и список файлов канонические: ручное редактирование JSON, README,
пересчёт их хешей, лишние/отсутствующие файлы и символьные ссылки отклоняются.
Это проверка согласованности пакета, а не криптографическая подпись его автора.

До завершения записи и внутренней проверки в каталоге остаётся `.incomplete`.
Прерванный процесс или ошибка записи не оставляют готовый пакет: проверка
такого каталога завершается ошибкой. Частичный каталог сохраняется для осмотра;
повторную попытку нужно выполнять в новом каталоге.

Полная копия содержит настройки и ключи, поэтому весь пакет следует хранить
приватно. На POSIX новый каталог создаётся с правами `0700`; Windows использует
правила доступа родительского каталога и установленной версии Python. Выберите
для назначения защищённую папку. Содержимое data-разделов не выводится в JSON.

Успешный `verify-recovery` сообщает `status=verified`, но сохраняет
`flash_authorized=false`. Принадлежность копии конкретной плате не определяется.
Приложение откатывает код, но не миграции настроек; запись полной flash,
изменение разметки/OTA и выполнение esptool этими командами не предусмотрены.
Аппаратные условия перед записью перечислены в README пакета. UA22, кириллица
и дисплей не переключаются: извлекается исходное приложение без модификации.

## Вывод и коды завершения

Без `--output` JSON выводится в stdout. С `--output` создаётся новый файл;
существующие файлы, включая исходные копии и образы, не перезаписываются.
Эти параметры относятся к `inspect-flash`/`plan-update`. `prepare-recovery`
выводит путь к manifest, `verify-recovery` — JSON с результатом проверки.
Для recovery-команд код `0` означает успех работы с файлами, `1` — отказ или
ошибку; код `2` используется argparse при неверных аргументах.

| Код | Значение |
| --- | --- |
| `0` | Проверки файлов прошли; это не разрешение на прошивку |
| `1` | Ошибка чтения/формата/manifest или файл вывода уже существует |
| `2` | Отчёт сформирован, но есть блокирующие условия; также стандартная ошибка аргументов CLI |

## Форматы и проверка

Разбор сверялся с документацией Espressif:
[образ приложения](https://docs.espressif.com/projects/esp-idf/en/v5.0.3/esp32s3/api-reference/system/app_image_format.html),
[разделы](https://docs.espressif.com/projects/esp-idf/en/v4.4.3/esp32s3/api-guides/partition-tables.html),
[CRC и выбор OTA-записи](https://github.com/espressif/esp-idf/blob/v4.4.7/components/bootloader_support/src/bootloader_common_loader.c).

На сохранённой копии T-Beam от 2026-10-01 и сборке `portable-tbeam-options`
подтверждены адрес `0x10000`, раздел 2 424 832 байта, приложение 2 411 424 байта
и запас 13 408 байт. Это повторная offline-проверка файлов; устройство и сервер
при разработке этих команд не использовались.
